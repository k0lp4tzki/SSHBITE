=== SSHBITE-Minimale-Rechte.md Zeile 193: `docs/side-effects.md:18-34`  ->  docs/side-effects.md
    18 | ## sudo: the "incident" mail on refused sudo
    19 | 
    20 | On every host SSHBITE first runs `sudo -n /bin/true` (with `privilege.mode: sudo`; sudo by its absolute
    21 | path `/usr/bin/sudo`, or `/bin/sudo` where that does not exist). Whenever sudo
    22 | refuses, it may mail a report to `mailto` (default `root`) with the subject
    23 | *"\*\*\* SECURITY information for HOST \*\*\*"*, if the host can send mail. Which refusals mail depends on
    24 | the sudoers options. Debian and Ubuntu ship `Defaults mail_badpass` in `/etc/sudoers`, and sudo's
    25 | `mail_no_user` is on by default. This is what we observed in the lab (Debian 12, sudo 1.9.13, Debian's
    26 | default sudoers, mail captured with a test mailer):
    27 | 
    28 | | Audit account on the host | What SSHBITE runs | Mail |
    29 | |---|---|---|
    30 | | `NOPASSWD` rule ([install.md](install.md#sudoers)) | `sudo -n …` | **none** |
    31 | | rule that requires a password | `sudo -n /bin/true` (probe) | **yes**: `sshbite : a password is required ; … COMMAND=/bin/true` – on every scan, also when the right password is given afterwards |
    32 | | rule that requires a password, wrong `--ask-sudo-password` | `sudo -S -k -p '' /bin/true` | **yes, a second one**: `1 incorrect password attempt` |
    33 | | no rule at all | `sudo -n /bin/true` | none (sudo only says "a password is required") |
    34 | | no rule at all, and `--ask-sudo-password` is the account's real password | `sudo -S -k -p '' /bin/true` | **yes**: `user NOT in sudoers` (the console says "This incident has been reported to the administrator") |

=== SSHBITE-Minimale-Rechte.md Zeile 313: `docs/install.md:156-194`  ->  docs/install.md
   156 | ## Sudoers
   157 | 
   158 | Without root, the collector cannot read other users' `~/.ssh` and `/etc/shadow`; the host is then
   159 | `partial`. The commands SSHBITE runs with sudo are fixed (see `sshbite collector show`). sudo is always
   160 | called by its absolute path – `/usr/bin/sudo`, or `/bin/sudo` only where `/usr/bin/sudo` does not exist
   161 | (decided by a fixed `test -x` on the host, never by the audit account's `PATH`); the table shortens that
   162 | to `sudo`:
   163 | 
   164 | | `privilege.mode` | Probe | Collector |
   165 | |---|---|---|
   166 | | `sudo` (default) | `sudo -n /bin/true` | `sudo -n /bin/sh -s` |
   167 | | `sudo-login` | `sudo -n -i /bin/true` | `sudo -n -i /bin/sh -s` |
   168 | | (with a sudo password) | `sudo -S -k -p '' /bin/true` | `sudo -S -k -p '' /bin/sh -s` |
   169 | | `none` | – | `/bin/sh -s` (unprivileged) |
   170 | 
   171 | Put this in `/etc/sudoers.d/sshbite` (mode 0440, check with `visudo -cf /etc/sudoers.d/sshbite`):
   172 | 
   173 | ```
   174 | # SSHBITE audit account: root for the read-only collector, no password, no lecture
   175 | Defaults:sshbite !lecture
   176 | sshbite ALL=(root) NOPASSWD: /bin/true, /bin/sh -s
   177 | ```
   178 | 
   179 | This line is for `privilege.mode: sudo`. With `sudo-login`, sudo runs root's login shell with the command
   180 | as `-c` argument, which a command list cannot express cleanly – use `NOPASSWD: ALL` there.
   181 | 
   182 | Be clear about what this grants: `/bin/sh -s` runs whatever arrives on stdin as root, so the line is
   183 | **equivalent to full root** for whoever holds the audit key. Restricting it to these two commands only
   184 | documents the intent and keeps other commands out of the sudo log. Protect the audit key accordingly
   185 | (mode 0600, a dedicated machine, `from=` restriction). What SSHBITE sends is fixed and reviewable:
   186 | [review.md](review.md).
   187 | 
   188 | If your policy demands a sudo password, drop `NOPASSWD:` and scan with `--ask-sudo-password`
   189 | ([scanning.md](scanning.md#sudo-passwords)). Be aware that with Debian's default sudoers every scan then
   190 | makes sudo send a *"SECURITY information"* mail per host, because the first, non-interactive probe is
   191 | refused ([side-effects.md](side-effects.md#sudo-the-incident-mail-on-refused-sudo)). Where `sshbite` has
   192 | no sudo rule at all, the host is scanned unprivileged and marked `partial`. Give the audit account a
   193 | password of its own that is used nowhere else and rotate it after the scan: a compromised host can imitate
   194 | a sudo prompt and capture it ([operations.md](operations.md#the-sudo-password)).
